# SecureChat Client API Contract

This document outlines the API contract and architectural boundary between the SecureChat application layer and the presentation/transport layers. Any future frontend (e.g., a TypeScript React application) must adhere to these models to interoperate with the SecureChat protocol.

## Architecture

```text
              APPLICATION (UI)
                   │
             Client App API
                   │
        ┌──────────┼──────────┐
        │          │          │
      Crypto   Moderation   State
        │          │          │
        └──────────┼──────────┘
                   │
             Transport API
                   │
          ┌────────┴────────┐
          │                 │
        TCP             WebSocket
```

The future web UI interacts **only** with the Client App API. It must not parse raw JSON frames, manage encryption keys, or manipulate socket state directly.

## Application Interface Operations

A standard implementation of the SecureChat app layer must expose the following asynchronous methods to the UI:

- `connect()`: Establishes the transport connection and sends the initial authentication payload.
- `disconnect()`: Cleanly closes the transport connection and transitions state.
- `reconnect_forever()`: Enters a bounded exponential backoff loop to restore the connection.
- `join_room(room: str)`: Emits a join frame for a specific room.
- `leave_room(room: str)`: Emits a leave frame for a specific room.
- `send_room_message(room: str, text: str)`: Moderates, encrypts, and transmits a message to a room.
- `send_direct_message(target: str, text: str)`: Moderates, encrypts, and transmits a direct message to a user.
- `send_key_exchange(target: str)`: Dispatches the client's public X25519 key to a peer for Diffie-Hellman derivation.

## Event Stream

The application layer provides a one-way event stream (`async generator` or `EventEmitter`) pushing strongly-typed events to the UI.

### Event Types

- **`ConnectionChanged`**: Fired when the `ConnectionState` transitions.
  - `state`: `disconnected` | `connecting` | `connected` | `authenticating` | `ready` | `reconnecting`
- **`MessageReceived`**: Fired when a successfully decrypted message arrives.
  - `sender`: Username of the sender.
  - `target`: Room or User it was sent to.
  - `text`: Decrypted plaintext.
- **`MessageStatusChanged`**: Fired when an outbound message progresses or fails.
  - `msg_id`: Unique identifier generated by the client.
  - `state`: `pending` | `sent` | `failed`
- **`PresenceChanged`**: Fired when a peer's status changes.
  - `user`: Peer username.
  - `room`: Room where the event occurred.
  - `status`: `joined` | `left` | `offline`
- **`KeyExchangeCompleted`**: Fired when a shared AES-GCM key has been successfully derived.
  - `peer`: Username of the peer.
- **`ModerationRejected`**: Fired when the local moderation model vetoes an outbound message.
  - `target`: Intended destination.
  - `text`: The rejected plaintext.
- **`ErrorOccurred`**: Fired for fatal transport or protocol errors.
  - `reason`: Description of the failure.

## Security Flow Constraints

1. **Moderation-Before-Encryption**: The Client API *must* apply local moderation to the plaintext `text` before it is passed to the crypto layer. If moderation fails, a `ModerationRejected` event is emitted, and the transport is never touched.
2. **Ciphertext Isolation**: The transport layer accepts a strictly formatted `dict` containing the `encrypted_payload`. The transport layer has zero dependencies on or knowledge of the crypto layer.
3. **Key Persistence**: Derived peer keys persist in-memory across reconnections. The client application layer retains the keys as long as it lives, preventing expensive re-negotiations after a brief network flap.

## Transport Implementation

To migrate to the Web, a `WebSocketTransport` class must be implemented to fulfill the `Transport` interface:

```typescript
interface Transport {
    connect(): Promise<void>;
    disconnect(): Promise<void>;
    send_frame(frame: Record<string, any>): Promise<void>;
    recv_frame(): Promise<Record<string, any>>;
}
```

The server backend will similarly require an upgrade to accept WebSocket handshakes and unmask WebSocket frames, translating them into the standard JSON protocol envelopes used by the router.

# Identity Binding & Authenticated Key Exchange

## 1. Identity Model

An identity uniquely represents a user in the system. The server relies on the username for routing, but cryptographically, a user is represented by a long-term Identity Key.

## 2. Selected Design: Option A (Signed Ephemeral X25519 Keys)

**Why this design?**
This is the standard pattern used in modern secure messaging protocols (e.g., Signal, Matrix). It cleanly separates long-term identity authentication from short-term session confidentiality, ensuring that we do not sacrifice the forward secrecy of the X25519 exchange while still providing strong MITM resistance.

### The Keys
* **Identity Key**: An Ed25519 key pair. Generated once per client lifetime (in-memory for this phase). Used exclusively for signing.
* **Ephemeral Session Key**: An X25519 key pair. Generated per session. Used for Diffie-Hellman key agreement to derive the AES-GCM shared secret.

## 3. Protocol Changes & Serialization

The `KEY_EXCHANGE` payload will be updated from a raw Base64 string to a structured JSON object.

### The Payload structure:
```json
{
  "identity_key": "<Base64 encoded Ed25519 public key (32 bytes)>",
  "ephemeral_key": "<Base64 encoded X25519 public key (32 bytes)>",
  "signature": "<Base64 encoded Ed25519 signature (64 bytes)>"
}
```

### Signature Generation & Verification
The signature is generated by the sender's Ed25519 private Identity Key.
To prevent signature reuse across different contexts or protocols, we use a strict canonical domain string.

**Signed Data Structure (Concatenated Bytes):**
```text
b"SecureChat-Identity-Binding-V1" || <Sender Username Bytes> || <Recipient Username Bytes> || <Ephemeral X25519 Public Key Bytes>
```

When Alice sends a key exchange to Bob, she signs:
`b"SecureChat-Identity-Binding-V1" + b"alice" + b"bob" + alice_x25519_pub`

Bob verifies the signature using Alice's provided `identity_key` and the identical concatenated byte structure.

## 4. Trust Model & MITM Protection

* **First Trust on First Use (TOFU)**: In this phase, Bob accepts the `identity_key` provided in the first `KEY_EXCHANGE`. 
* **MITM Detection**: If a malicious server replaces the `ephemeral_key` with its own, the signature will fail to verify because the server does not possess Alice's Ed25519 private key to generate a valid signature over the new ephemeral key. If the server tries to replace both the `identity_key` and the `ephemeral_key` (total spoofing), Bob's client would theoretically accept it on first contact (TOFU), but in a real-world scenario (Phase 5D+), Alice and Bob would verify their Identity Key fingerprints out-of-band. For now, this mathematically binds the ephemeral key to the claimed identity key, strictly preventing silent ephemeral key substitution by a relay.

## 5. Implementations

### Browser (TypeScript)
* **Library**: `@noble/curves/ed25519` for both X25519 (session) and Ed25519 (identity).
* **Storage**: Both private keys exist purely in `WebCryptoProvider`'s memory. They are lost on reload (by design for this phase).

### Python
* **Library**: `cryptography.hazmat.primitives.asymmetric.ed25519` for the Identity Key. `x25519` for the ephemeral session key.
* **Storage**: Resides entirely in `ChatCrypto` RAM.

### Reconnect Behavior
* Reconnections will reuse the existing in-memory Identity Key and Ephemeral X25519 key. No new generation is required as long as the application process runs.

## 6. Security Invariants Preserved
* Server never sees Identity Private Keys.
* Server only routes the JSON payload and never inspects the AES-GCM plaintext.
* Existing AES-GCM and Moderation boundaries remain completely intact.
